## The finding that matters

**Exactly the releases that have breaking changes are the releases an operator cannot read, on any
Windows console with a legacy codepage.**

```text
$ agw guide show concept-release-notes/v0-14-0
Error: UnicodeEncodeError: 'charmap' codec can't encode character '⚠' in position 128:
character maps to <undefined>
(full traceback written to ~/.config\agentworks\logs\error.log; rerun with --debug or AGW_DEBUG=1)
exit 1
```

Five of the fourteen packaged release topics fail this way: `v0-14-0`, `v0-13-0`, `v0-12-0`,
`v0-11-0`, `v0-3-0`. Scanning `cli/CHANGELOG.md` for characters outside cp1252 returns those same
five versions and no others, with a single distinct offender, U+26A0, appearing in all five as
release-please's breaking-changes heading. The correlation is exact: the set of unreadable topics is
the set of releases with a breaking-change section.

That makes this self-perpetuating rather than a one-off content problem. The marker is generated by
release tooling, so every future release with a breaking change ships its own unreadable topic, and
no author action introduces or avoids it.

Failure is mode-independent, as expected from `render_release_topic(version)` taking no mode:
`--agent` and `--human` fail identically on all five. `PYTHONUTF8=1` and `PYTHONIOENCODING=utf-8`
each render all fourteen topics cleanly, which localizes this to stdout encoding rather than to
parsing, escaping, or the packaged content.

Two things make it worse than its blast radius suggests.

First, it fires on the exact path the guide tells an agent to walk. `concept-release-notes` says to
run `agw version` and then request that version's topic. Following that instruction verbatim on
0.13.0 or 0.14.0 crashes. An upgrade-safety question routed through the guide is answerable for
every release except the ones where the answer matters.

Second, the failure is framed as a defect in the guide. It renders as a bare codec error and writes
a traceback to `error.log`, which reads as corrupt or unreadable packaged content. Nothing points at
the workstation's encoding, and nothing names the one-variable workaround that resolves it. An agent
that trusts the framing will report a broken guide, or worse, try to repair the changelog.

### Where a fix belongs

`typer.echo` at `cli/agentworks/cli/commands/guide.py:57` writes to a `cp1252` stream, and nothing
in the CLI reconfigures stdout: searching the tree for `reconfigure`, `PYTHONIOENCODING`, or a
stdout encoding override returns nothing, while `errors="replace"` already appears at eight
subprocess and log-handler sites. Subprocess I/O is hardened against undecodable bytes; the CLI's
own stdout is not.

That argues for reconfiguring stdout to UTF-8 with `errors="replace"` in `_entry.py`'s `main()`,
alongside `set_handler(TyperHandler())`, rather than transliterating inside
`escape_release_evidence` or `sanitize_terminal_output`. A guide-local fix leaves every other
command one non-Latin-1 character away from the same crash, and `sanitize_terminal_output` is the
wrong owner: its job is stripping terminal control sequences, not encoding negotiation.

The latent scope is worth stating because it is currently invisible. Every file under
`guide-content/` is cp1252-clean today, which is why only the changelog-derived path trips. That is
a property no test or lint asserts, so the first check mark, arrow, or en-dash added to a retained
concept shell breaks that topic on Windows, and it breaks for the operator who added it only if they
are not on Windows. If the entrypoint fix is declined, a check that packaged guide Markdown is
encodable in the running stdout codec would at least make the constraint enforced rather than lucky.

## Smaller things, in descending order

### `agw guide list` emits CRLF, and it is the one machine-readable guide output

The docs point at `agw guide list` as the discovery surface, so the obvious agent move is to iterate
it in a shell. In Git Bash the carriage return rides into the topic argument and every lookup fails
with an unknown-topic error naming the topic plus a trailing `\r`.

Ordinary Windows text-mode behavior, and every other command shares it. It matters more here because
`list` exists specifically to be consumed by a program, and its failure mode is not obviously an
encoding artifact: the error says the topic is unknown, which reads as a stale or misspelled name.
It cost this session a wrong intermediate conclusion, briefly measuring the guide as nearly
command-free because all thirty lookups had failed silently into error text. Forcing a bare newline
on `list`, or documenting the strip, would close it.

### Agent mode is close to a no-op outside the index

Diffing `--agent` against `--human`, `concept-troubleshooting` and `concept-secrets` are
byte-identical, and of the topics compared only `concept-onboarding` differs, by thirteen added
lines. This matches the documented contract, that a shell "may" fence an agent-only passage, so it
is not a defect. It is worth a deliberate decision rather than drift, though, because the fencing
machinery, its mode plumbing, and the `--agent/--human` surface currently buy one topic's worth of
delta. Either more topics have agent-only context worth writing, or the index shell is doing
essentially all of the mode-specific work and the per-topic capability is speculative.

### The mode heuristic inverts the more common ambiguous case

`select_guide_mode` falls back to agent mode when stdout is not a TTY, so a human running
`agw guide > notes.md` or piping into a pager gets agent-targeted content. Low stakes while the
delta stays small.

The sharper edge is that `HARNESS_SIGNATURES` contains only `CLAUDECODE=1`. Codex ships a
first-class Agentworks package that bootstraps by invoking `agw guide --agent`, but has no
signature, so a Codex session on a TTY silently receives human mode. Explicit `--agent` in the
bootstrap covers the scripted path; anything Codex runs afterward without the flag does not. A Codex
signature looks cheap next to shipping the package.

### The index does not disclose the release-note address form

The index closes with "4 other concepts are available. Run `agw guide list`", which is accurate for
concepts, and `list` then returns thirty lines because fourteen packaged release topics are not
concepts. The versioned address form under `concept-release-notes` appears only inside that topic.
An agent that wants one specific version either reads a topic it does not otherwise need or infers
the form from `list` output. One clause in the index removes a round trip.

### The evidence escaping is inert where it ships

`escape_release_evidence` output lands inside a fenced `text` block, where the backslashes have no
effect and render literally, including the escaped hashes of the heading and the escaped backticks
and hyphens of the migrate command. Sensible belt-and-braces if the fence were ever dropped, but as
shipped it degrades the readability of the one surface deliberately presented as evidence. It also
carries a small copy hazard, since the escaped form of `agw resource migrate --all` is a plausible
thing for an agent to lift verbatim into a shell, where the escapes are not inert. Escaping at
render time based on whether the fence is used would keep both properties.

## What held up, and is worth not regressing

Verified rather than read, since these are the properties most likely to rot quietly:

- **No command drift.** Extracted every `agw` invocation signposted across all sixteen concept
  topics and checked each against the live CLI: 28 distinct commands, all present. The four flag
  spellings the topics name (`resource list --include-disabled`, `--kind`, `--origin`, and
  `doctor --output json`) all execute. For static teaching that points at command-owned facts by
  design, this is the load-bearing property, and it currently holds exactly.
- **The topic lookup boundary is tight.** A parent-directory traversal, a traversal nested under a
  valid topic, a trailing slash, the empty string, and an embedded NUL are all rejected as
  `invalid`, the reserved `_index` shell is not addressable, and `invalid` versus `unknown` cleanly
  separates a malformed name from a well-formed absent one. Useful to an agent deciding whether to
  correct a name or stop.
- **The posture content changes agent behavior, not just tone.** `concept-assistant-agent` stating
  that guide output is instructional but grants no authority forestalls the failure mode where an
  agent treats teaching as a work order. `concept-secrets` requiring the possible prompt or
  biometric effect be stated before `--allow-interaction`, and `concept-reporting-bugs` requiring a
  redacted draft stay local absent authorization, are specific enough to be followed. This is the
  part hardest to reconstruct if it is ever refactored for brevity.
