# Prior Art Research: Declarative Schema for Capabilities, Resources, and Config

Date: 2026-07-31

## Executive summary

We surveyed how other ecosystems let pluggable components declare configuration schema and what they
build on top of it. Three patterns dominate, and they are remarkably consistent across languages and
domains:

1. **Types are the single source of truth; schema is derived, never hand-maintained in parallel.**
   Pydantic (`model_json_schema()`), msgspec (`schema()`), Kubernetes controller-gen (Go types plus
   markers), and Terraform's typed attribute structs all reflect schema out of the code that already
   validates. The one ecosystem that duplicates (Ansible's `argument_spec` beside a `DOCUMENTATION`
   YAML block) is the cautionary tale: the two drift, and third-party tools exist solely to
   re-derive one from the other.
2. **Discriminated (tagged) unions are a first-class, solved primitive.** "This sub-table's shape
   depends on which plugin the parent names" is exactly Pydantic's `Field(discriminator=...)`,
   OpenAPI's `discriminator` + `mapping`, msgspec's `tag_field`, and JSON Typedef's native
   discriminator form. Our capability-embedded config is the textbook case, not an exotic one.
3. **Docs and samples are generated by merging schema-derived reference material with hand-authored
   prose; never from schema alone.** Terraform's tfplugindocs (schema descriptions + per-resource
   Markdown templates + example files, auto-stubbing missing templates) is the mature reference
   implementation of this pattern.

The honest gap: **no mature Python tool generates commented, human-friendly sample config from a
schema.** Rust has `toml-scaffold` / `toml-comment` proving the pattern; in Python it is a small
custom generator we should budget as real (if modest) implementation work.

## Findings by dimension

### 1. Types-as-schema declaration

- **Pydantic v2** is the Python default: models carry types, constraints (`Field(...)`),
  descriptions, and defaults; `model_json_schema()` emits JSON Schema (2020-12). Strict-mypy
  friendly, Rust-core fast, frozen models supported. Docs tooling exists on both major doc stacks
  (autodoc-pydantic for Sphinx, griffe-pydantic for MkDocs).
- **msgspec** is the lighter alternative (fast structs, `msgspec.json.schema()`, tagged unions via
  `tag_field`, native TOML encode/decode) but has a far smaller downstream ecosystem; nothing like
  autodoc-pydantic exists for it.
- **apischema** and **dataclasses-jsonschema** derive JSON Schema from plain dataclasses; smaller
  communities, less momentum.
- **typedload** loads dicts into typed structures but emits no schema at all; ruled out.
- Outside Python, **controller-gen** (Go struct tags + `+kubebuilder:` comment markers to OpenAPI
  v3) and **Terraform's provider protocol** (typed `Schema`/`Attribute` structs served over a
  `GetProviderSchema` RPC) validate the same pattern: derive from typed code plus light annotation.

**Decision informed:** adopt Pydantic v2 as the declaration layer for capability config and resource
kinds. An in-house field-spec was seriously considered (see refuted section) and rejected once scope
grew from capability blobs to all resource schema.

### 2. Discriminated unions for capability-embedded config

Pydantic supports the string form (`Field(discriminator="platform")` with a `Literal` tag per
member) and a callable `Discriminator` for dynamic dispatch. A runtime-populated plugin registry can
rebuild the union per process (models are ordinary Python objects; `create_model` or plain
`Annotated` union assembly at registration time works). Emitted JSON Schema uses `oneOf` plus
OpenAPI-style `discriminator`/`mapping`, which downstream tools understand.

**Decision informed:** the consuming-resource surfaces (`platform_config`, `provider_config`,
`harness_config`, secret backend mappings) become discriminated unions assembled from the capability
registry at registration time.

### 3. JSON Schema as the interchange format

Once JSON Schema exists per kind, a broad consumer ecosystem lights up:

- **yaml-language-server** (used by VS Code and most LSP editors): completions, hover docs, and
  diagnostics for YAML manifests via a `# yaml-language-server: $schema=...` modeline or a schema
  catalog. Directly applicable to our resource manifests.
- **taplo** ("Even Better TOML" in VS Code): the same for TOML, via `taplo.toml` glob mapping or a
  `#:schema` magic comment. Applicable to config.toml. Caveat: taplo validates against JSON Schema
  **Draft 4**; Pydantic emits 2020-12 by default, so the editor-facing schema may need a
  draft-4-safe subset.
- **json-schema-for-humans** and **jsonschema2md** render Markdown/HTML reference docs from a schema
  file.
- **SchemaStore** auto-associates schemas by filename for well-known formats; only relevant if we
  ever want zero-config editor association for operators.

**Decision informed:** emit JSON Schema per resource kind (and per capability config union) as a
build/CLI artifact; associate it with generated manifests via modeline.

### 4. Docs and explain surfaces

- **tfplugindocs** merges provider schema (with per-attribute `Description` and
  `MarkdownDescription`) into hand-authored per-resource templates plus example files, and
  auto-generates a stub template when one is missing. Schema supplies the reference tables; humans
  supply the narrative.
- **Kubernetes structural schemas**: since CRDs must be fully typed at every node, the API server
  can prune unknown fields, apply defaults, and serve `kubectl explain` from the schema tree. The
  lesson: keep every union branch concretely typed and an "explain this field" surface falls out.
- **Ansible** (negative lesson): schema (`argument_spec`) and docs (`DOCUMENTATION` YAML) are
  authored separately, drift chronically, and are reconciled only by CI checks and third-party
  re-derivation tools (`ansible-argspec-gen`).
- **VS Code `contributes.configuration`**: many independently-authored extensions each contribute a
  self-contained schema fragment; the host merges them into one navigable settings schema driving
  UI, completion, and validation. Structurally the closest match to "many capability plugins, one
  merged schema surface."
- **Home Assistant / voluptuous-openapi**: an existing imperative-validator ecosystem that bolted on
  schema emission by converting validators to OpenAPI. Proof that "keep imperative validation, emit
  schema separately" is possible, but it reintroduces a translation layer we do not need if the
  declaration is a model to begin with.

**Decision informed:** generated field-reference material merged with hand-authored prose blurbs
(tfplugindocs shape) for samples and guides; a schema-backed describe/explain surface in the CLI.

### 5. Commented sample generation

No mature Python tool turns a schema into a commented TOML/YAML sample. Rust's `toml-scaffold`
(built on schemars-derived JSON Schema) and `toml-comment` prove the pattern: doc comments become
config comments, defaults become values. In Python:

- `pydantic_yaml` can dump an instance to YAML and can carry descriptions into comments (via
  ruamel.yaml), but only from an instantiated model, YAML only.
- Our bundled samples are fully-commented-out YAML (every line `#`-prefixed), so generation is plain
  text emission over a schema walk; no comment-capable writer is even required.
- For TOML output, **tomlkit** (already a runtime dependency) supports writing comments, contrary to
  the common claim that Python TOML writers are comment-blind (`tomli-w` and `toml` are; tomlkit is
  not).

**Decision informed:** write a small in-house sample generator that walks the schema (descriptions,
defaults, examples, discriminator mapping; one union arm rendered, alternatives commented out) and
merges per-capability hand-written prose blurbs. Budget a few hundred lines.

### 6. TOML-specific concerns

- TOML has no null: `Optional[X] = None` must map to key-omitted, both when validating and when
  generating samples.
- TOML has native datetime/date/time types; JSON Schema models these as `format: date-time` strings.
  Python's tomllib yields real `datetime` objects, which Pydantic accepts natively, so validation is
  clean; only a TOML _writer_ needs to know a field is logically a datetime, which the schema's
  `format` keyword preserves.

## Refuted / do-not-rely-on

- **"Python TOML writers cannot write comments."** False for tomlkit, which we already ship.
- **Schema inference from example instances** (helm-schema-gen and kin): universally documented,
  including by their own authors, as a rough starting point only; cannot infer enums, patterns,
  conditional requirements, or closed-world key sets. Not a path to schema.
- **JSON Typedef (RFC 8927)**: cleaner native discriminator, but abandons the entire JSON Schema
  consumer ecosystem (taplo, yaml-language-server, doc renderers). Rejected.
- **CUE**: unifies schema, defaults, and data in one language; architecturally elegant, but a new
  language and toolchain for operators and authors. Rejected for this project.
- **pydantic-settings**: solves file/env/secret layering we already have bespoke machinery for;
  adopting it would be a second migration with little payoff. Deferred indefinitely.
- **An in-house field-spec DSL** (Terraform-attribute style): right-sized when scope was capability
  blobs only; once the goal includes all resource kinds and ideally config, it converges on
  reimplementing Pydantic (nested tables, unions, constraints, error paths, schema emission) with
  fewer tests. Rejected in favor of Pydantic v2.

## Open questions

- **Draft-4 subset for taplo**: whether the emitted 2020-12 schema needs a down-leveled variant for
  TOML editor tooling, or whether the config.toml surface is small enough not to bother initially.
- **Error-position bridge**: Pydantic `ValidationError.loc` paths carry no source positions; the
  design must map them onto YAML marks (and the TOML section line map, for whatever config surface
  remains) to preserve today's file/line error framing. Shape TBD in the HLA/LLD.
- **Union assembly timing**: whether capability config unions are rebuilt per process at registry
  finalize (plugin registration order) or assembled lazily per validation call; interacts with the
  plugin system's opt-in gating.
- **Custom metadata vocabulary**: the exact `Annotated` metadata for reference-typed fields
  (secret/resource refs with kind) and owner-templated default secret names, and how it round-trips
  into emitted JSON Schema (`json_schema_extra`) for docs without confusing editor tooling.
